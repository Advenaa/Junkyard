## Critical

### [C-001] SSRF bypass in RSS — validateUrl called without await
- **Location**: src/ingest/rss.ts:31
- **Category**: security
- **Status**: open
- **Found**: 2026-04-02
- **Description**: `validateUrl()` is async but called without `await`. A Promise is always truthy, so `!validateUrl(link)` is always false. SSRF protection is completely non-functional for RSS article extraction. An attacker controlling an RSS feed can probe internal infrastructure or read cloud metadata (169.254.169.254).
- **Evidence**: `if (!validateUrl(link)) { return originalContent; }` — compare with correct usage in news.ts: `const validation = await validateUrl(url);`
- **Suggested fix**: Add `await`, destructure result, check `.valid`.

### [C-002] Summarize pipeline loses items on partial chunk failure
- **Location**: src/process/summarize.ts:366-413
- **Category**: data-integrity
- **Status**: open
- **Found**: 2026-04-02
- **Description**: If chunk N succeeds but chunk N+1 throws, `markProcessed(pool, batchId)` at line 409 still marks ALL claimed items as `processed`. Items in failed chunks never get summaries but are permanently marked done. They will never be re-processed. Additionally, summary insert and markProcessed are not in a transaction — crash between them creates duplicate summaries on recovery.
- **Evidence**: `catch (err) { log.error(..., 'Failed to process chunk, skipping'); }` then unconditional `await markProcessed(pool, batchId);`
- **Suggested fix**: Track successfully processed item IDs. Only mark those as processed. Reset failed items to `ready` or `failed`. Wrap in transaction.

### [C-003] Shutdown doesn't stop scheduler or Discord gateway
- **Location**: src/index.ts:29-40
- **Category**: reliability
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Shutdown calls `app.close()` + `pool.end()` but never invokes `scheduler.stop()` or `discordAdapter.disconnect()`. Cron jobs keep firing during shutdown, potentially starting new LLM calls. pool.end() kills DB connections under running queries, leaving items stuck in `processing`.
- **Evidence**: `const shutdown = async () => { ... await app.close(); await pool.end(); process.exit(0); };` — scheduler.stop() exists but is never called.
- **Suggested fix**: Wire shutdown: (1) stop cron, (2) drain in-flight jobs (scheduler has 25s drain), (3) disconnect Discord, (4) close HTTP server, (5) drain pool.

### [C-004] Daily synthesis always passes empty correlated entities
- **Location**: src/process/synthesize.ts:341
- **Category**: llm-pipeline
- **Status**: open
- **Found**: 2026-04-02
- **Description**: `buildDailyUserMessage(summaries, dedupedEvents, [], yesterdayTldr)` — hardcoded empty array for correlated entities. Stage 2 cross-source correlation results never reach Stage 3. This defeats the core value proposition of multi-source signal amplification. The daily report has no awareness of which entities were verified across multiple sources.
- **Evidence**: Line 341: third argument is literal `[]`.
- **Suggested fix**: Call correlator before daily synthesis, pass results to `buildDailyUserMessage`.

### [C-005] entity_mentions.created_at stores ISO string in INTEGER column
- **Location**: src/knowledge/entities.ts:51,279 vs migration line 117
- **Category**: data-integrity
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Migration defines `created_at INTEGER NOT NULL` (epoch ms) but code stores `new Date().toISOString()`. Postgres silently casts or fails. Correlation queries comparing epoch-ms cutoffs against ISO strings produce incorrect results — cross-source correlation (a core feature) is broken.
- **Evidence**: `const now = new Date().toISOString();` used for `entities.first_seen`, `entities.last_seen`, `entity_mentions.created_at` — all INTEGER columns.
- **Suggested fix**: Use `Date.now()` consistently for all integer timestamp columns.

## High

### [H-001] Secrets printed to stdout before logger init
- **Location**: src/config.ts:77,83-84
- **Category**: security
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Auto-generated API_KEY and SESSION_SECRET logged via `console.warn` before Pino is created. Full secrets in plaintext in pm2/systemd logs. API key = admin access, session secret = cookie forgery.
- **Evidence**: `console.warn(\`WARNING: API_KEY not set — generated: ${apiKey}\`);`

### [H-002] No auth middleware on any API route
- **Location**: src/server.ts:36-76
- **Category**: security
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Routes for /api/v1/reports, /sources, /config, /search, /feed, /chat, /users have no `requireAuth`/`requireAdmin` preHandler. Auth functions exist in middleware.ts but are never imported in server.ts. All endpoints currently return `{ todo: true }`, but the pattern will be inherited by future implementations.
- **Evidence**: No import of requireAuth/requireAdmin in server.ts. No preHandler on any route.
- **Suggested fix**: Register requireAuth as preHandler on all /api/v1/* routes (except health/auth). Use requireAdmin on PATCH /config and GET /users.

### [H-003] Content hash dedup uses only first 200 characters
- **Location**: src/normalize/index.ts:70
- **Category**: data-integrity
- **Status**: open
- **Found**: 2026-04-02
- **Description**: `sha256(source + sourceId + content.slice(0, 200))` — two different messages sharing the same first 200 chars (common with RSS boilerplate, bot-generated Discord messages) are treated as duplicates. Real duplicates with different first 200 chars bypass dedup.
- **Evidence**: `const contentHash = sha256(item.source + item.sourceId + item.content.slice(0, 200));`
- **Suggested fix**: Hash full content or at least first 2000 chars. Normalize whitespace before hashing.

### [H-004] Dedup check+insert is not atomic (TOCTOU race)
- **Location**: src/normalize/index.ts:71-77,167-184
- **Category**: data-integrity
- **Status**: open
- **Found**: 2026-04-02
- **Description**: SELECT checks for duplicate hash, then INSERT happens later (possibly seconds later after translation LLM call). Concurrent normalize calls can both pass the check. No UNIQUE constraint on `items.content_hash`.
- **Evidence**: Check at T1: `SELECT id FROM items WHERE content_hash = $1`, Insert at T2: `insertItem(pool, {...})` — no transaction, no unique constraint.
- **Suggested fix**: Add UNIQUE index on content_hash. Use INSERT ... ON CONFLICT DO NOTHING, check rowCount.

### [H-005] Entity alias silently points to wrong entity

## Cycle 2 — Performance (C)

### [C-006] Vector cache — unbounded memory growth with no eviction
- **Location**: src/vector-cache.ts:40-116
- **Category**: performance
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Three Map<string, Float32Array> grow without bound. At 768 dims × 4 bytes = 3KB/vector, 100K summaries = ~307MB. No LRU, no TTL, no max-size. load() does `SELECT target_id, vector FROM embeddings` with no LIMIT. Over months of 24/7 operation → OOM.
- **Suggested fix**: LRU cache with max size. Fallback to Postgres-side cosine similarity (pgvector) for cold vectors.

### [C-007] Silhouette score computation O(n²*k) blocks event loop
- **Location**: src/process/narratives.ts:67-122,195-205
- **Category**: performance
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Triple-nested loop: n points × n distances × k candidates × 768 dims. 100 summaries = ~60M float ops, all synchronous. Blocks HTTP, heartbeats, WebSocket for seconds.
- **Suggested fix**: Move to worker_threads, or use simplified silhouette (centroid-only, O(n*k)).

### [H-018] Vector search is O(n) linear scan per query
- **Location**: src/vector-cache.ts:83-98
- **Category**: performance
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Every chat query iterates ALL vectors, computes 768-dim cosine sim, sorts entire array. 50K vectors = ~150ms CPU blocking per search. Multiple concurrent chat users serialize.
- **Suggested fix**: Use ANN index (hnswlib-node/usearch) or pgvector with HNSW index.

### [H-019] 10-connection pool shared across all consumers — starvation risk
- **Location**: src/db/connection.ts:8
- **Category**: performance
- **Status**: open
- **Found**: 2026-04-02
- **Description**: Pool max:10 shared by scheduler (50+ parallel sources), embed pipeline, health monitor, pulse, synthesis, retention, chat, narratives. During peak with 50+ sources polling, pool saturates → 5s connection timeout → queries fail.
- **Suggested fix**: Increase to 20-25. Add pool metrics monitoring. Consider separate pools for critical vs background paths.
